# Code review, 2026-10-16

A whole-codebase review of `main` at `c3fb8b9` (after #126), for design and coupling first, then bugs and algorithmic
improvements. Everything below was verified by reading the code path, and the measurements were taken on the corpus
replay `PylonAIE_v4-TvZ` (760 observations, 157 units at the median) with `tests/corpus` and no game running.

Findings are ranked within each section. "Verdict" says how sure the finding is: **confirmed** means reproduced or read
end to end; **design** means a judgment call for the owner.

## Summary: the six that matter most

1. **`Unit` and `_Tracker` hold each other** (1.1): a unit cannot exist or be tested without a tracker, and both write
   the change log. The one structural change worth planning.
2. **A structure destroyed and rebuilt out of sight is never reported dead** (2.1, reproduced): the tracker merges
   the new structure into the old unit by position.
3. **Placement grids are rebuilt from scratch every observation** (3.1, measured): the first `is_free` of a turn costs
   six times the whole observation pipeline.
4. **The tech tree knows one creation ability per type** (2.5): a nuke reads `KEEPS_ORDERS`, and the way back of every
   form change "makes nothing", so `in_production` and the order book draw wrong conclusions from that absence.
5. **`Tile` leaks through `Point`** (2.6): arithmetic, equality and two of four `__contains__` implementations treat a
   tile address as a point; `TileSet.closest_point_to` and `distance_transform(outside=False)` return wrong answers.
6. **Twenty-two private imports cross package boundaries, and `gamemap` depends on `placement`** (1.2, 1.3): the
   public surfaces of `geometry` and `gamedata` lack what their siblings need.

Everything the generators, ids, costs and the protocol state machine were checked for came back clean; the
protocol's defects are edge cases in error translation and one measured 12x recording cost.

## 1. Design and coupling

### 1.1 `Unit` and `_Tracker` hold each other (design, biggest)

`Unit` keeps a `_tracker` and reaches through it for the data tables (`type_data`, `footprint`), the upgrade view
(`weapons`, `speed`, `armor`), the builder tracker (`construction`, `builder`) and the tag index (`add_on`,
`engaged_target`, `_unit_target_of_order`). In the other direction, `Unit._update` writes into
`tracker.last_changes` (`units_alliance_changed`, `units_type_changed`) and swaps its own class through
`object.__setattr__(self, "__class__", ...)`. So a unit cannot exist, or be tested, without a whole `_Tracker`, and
the tracker's change log is written from two places.

Suggested shape: `_update` returns what changed (or the tracker compares before and after, as the comparer already
does), and `Unit` takes a narrow read-only context (tables, `get_by_tag`, upgrade view) instead of the tracker. The
in-place class swap can stay; it is the two-way write that costs.

### 1.2 Private imports across packages: 22 (design)

Twenty-two `from sc2nachos.<pkg>._<module>` imports cross a package boundary (list: `uv run python -c` over
`src`, pattern `from sc2nachos\.(\w+)\._`). The worst offenders:

- `orders` imports `gamedata._techtree.ABILITIES_SENT_AS_ANOTHER` and `gamedata._sent_as`, though every row already
  carries `AbilityData.sent_as`; the order book re-derives what `GameData` holds.
- `placement` imports `geometry._footprint._is_count/_margin_sides` and `state._state._State` (for `creep` only).
- `gamemap` imports `placement._townhall_zones` and `units._tracking._UnitTracker`.
- `state` imports `gamemap._image_data`.

A private import across packages means the exporting package lacks a public spelling. Either promote the helper
(`image_tiles`, `coordinates`, `_margin_sides` as a `Margin` normalizer) or move the caller.

### 1.3 Layering is inverted around `gamemap` and `placement` (design)

The package graph (runtime imports only):

```
protocol, geometry, ids, match, constants      <- leaves
gamedata  -> geometry, ids
units     -> gamedata, geometry, ids, upgrade_reader (top-level module, which imports units back)
gamemap   -> geometry, units, placement, protocol
placement -> gamedata, geometry, units          (TYPE_CHECKING: orders, state)
state     -> gamedata, gamemap, geometry, units
orders    -> gamedata, geometry, protocol, state, units
events    -> geometry, ids, match, state, units
```

Two things stand out. `gamemap` depends on `placement`, though placement is a per-observation reading above the map;
the shared `_keep_townhalls_off_resources` belongs below both (gamedata or geometry), or `Expansion` belongs in a
package of its own above both. And `upgrade_reader` is a public top-level module whose only callers are
`units._tracking._upgrade_tracker` and `_game`, while it imports `units`; the cycle only works because `_tracking`
is loaded late. Move it under `units/_tracking` (or `enemy`) and drop the public name.

### 1.4 `_State`, `PlacementGrids` and `OrderBook` form a web, not layers (design)

`_State(observation, tracker, game_map)` reads units for `supply` and `production`; `PlacementGrids` holds the
`_State` (for creep), the present units, the tables and the `OrderBook` (for `issued_to(include_sent=True)`);
`OrderBook` and `_BuildSites` read `unit._latest_report.orders`, the raw protobuf, directly. `_Game` is the right
composition root, but each part should take the narrow input it reads (a creep grid, a callable for ordered builds, a
unit's `orders`) rather than its neighbor whole. The raw `UnitOrder` protobuf is read in four packages
(`units`, `orders`, `placement`, `state`); keeping it inside `units` would make the others testable with plain
`UnitOrder` values.

### 1.5 The event order is spelled out three times (design, small)

`_Game.report` is ~45 lines of hand-ordered `hand_on` calls; `tests/support.py` repeats the order as `HAPPENINGS`,
and `docs/events.md` a third time. A single table `(event type, changes attribute, tuples)` in `_game.py`, which
`report` iterates and the test imports, would leave one place to edit.

### 1.6 Smaller design points

- `Api.client` exposes the protocol `Client`: a bot can `client.act` around the order book or `client.step` and
  desynchronize `Api.step`. Slice 6 (debug, chat) is the moment to replace it with typed methods.
- The generic bus (`EventBus`, `EventFilter`, `_Handler`, `_EventSubscriptions`) has no game dependency, yet lives
  in a package that imports `state` and `units`; splitting it is cheap and would let it be tested and reused alone.
- `AbilityId.read` raises `UncuratedIdError` on read paths a bot touches every turn (`OwnUnit.orders`,
  `Passenger`, `Effect`, `UnitCommand`), while `OrderBook._ability_of_unit_order` and
  `_BuildSites._builds_ordered_to` tolerate the same id with `AbilityId.get(...) or AbilityId.NULL`. Both policies
  are defensible; having both means one unknown id in a unit's queue ends a bot's game, but only if the bot reads
  `orders`. Pick one, and say it in `docs/curating-ids.md`.
- `Unit.type_data` and `Unit.is_structure` index `game_data.units[...]` while `footprint` and
  `_Game._is_structure` use `.get`. The corpus shows no observed type missing from the table (checked over all seven
  games), so this is consistency, not a live bug.
- `TilePath` is exported from `geometry` with no producer anywhere (`path_distance_from` returns a `Grid`), and
  `Installation.replays` and `Client.save_replay` have no caller outside tests while `--replay-file` is accepted as
  "not yet supported". Some twenty more geometry names have only their own tests as callers (`Grid.smoothed`,
  `distance_transform`, `minimum`, `maximum`, `Rectangle.perimeter`, `Circle.intersections_with`,
  `Point.rotated` and the like). Each passes the checklist's letter; worth a pruning pass before publishing.

## 2. Bugs and misleading contracts

### 2.1 A structure destroyed and rebuilt out of sight is never reported dead (reproduced)

`_UnitTracker._identify_new_tags` matches a new tag to a departed unit by `(alliance, x, y)` and the vision/fog
swap alone, deliberately ignoring the type. An enemy extractor killed while out of sight and rebuilt on the same
geyser is listed, when the spot comes back into vision, at the same position with a new tag: NachOS treats it as the
old unit coming out of the fog. No `UnitDiedEvent`/`UnitFoundDeadEvent`, no `EnemyUnitFirstSeenEvent`, and the
unit's `id` and `first_alliance` are the old one's. The same holds for any structure rebuilt centered on the same
tile. Mitigation: when the types differ and the pair is not a known morph (`TECH_TREE` has the morph edges), treat it
as a death and a new unit; a same-type rebuild remains undetectable from the raw interface and should be noted in
`docs/game-behavior.md`.

### 2.2 `Api.upgrades` docstring promises a raise that cannot happen there (confirmed)

It says "Raises `UncuratedIdError` if one is one the curated ids leave out", but the read is
`_UpgradeTracker.own`, a plain frozenset. The raise happens in `_UpgradeTracker.update`, inside `Api.play` when the
observation is taken in. Fix the docstring (and check `Api.effects`/`action_failures`, which do raise lazily, read
the same way).

### 2.3 `OrderBook` reads `ABILITIES_SENT_AS_ANOTHER` instead of the row (confirmed, low)

`issue` and `_send` look the ability up in the tech tree constant while `self._game_data.abilities[ability].sent_as`
holds the same mapping. Harmless today, but a `GameData` built from other tables (tests use `make_tables`) silently
disagrees with the order book.

### 2.4 Protocol, launch and util (each confirmed by a snippet)

- **`protocol/_websocket.py:53-77`: after a timeout the transport serves stale answers.** A `recv` that raises
  `WebSocketTimeoutException` makes request 1 raise `ConnectionTimeoutError`; request 2 then returns request 1's late
  reply with no error, and `Client` notices only when the response kind differs (two observations in a row pass).
  Reachable only with `timeout=` on `WebSocketTransport.connect`, which no in-repo caller passes, but it is public.
  Fix: close the socket on any mid-request failure, or number requests (`Request.id`, which the game echoes) and
  reject a mismatched reply.
- **`protocol/_websocket.py:55-66`: a non-`ConnectionError` `OSError` from the socket escapes `request()`
  untranslated** (`connect` translates the same class; `request` does not). Add an `except OSError` clause raising
  `ConnectionClosedError`.
- **`util/_time_series.py:150-158`: any bounded slice of an empty series raises `TypeError`** (`int - None`):
  `TimeSeries.empty(float)[3:5]`, `[:5]`, `[3:]` and the matching assignments. Return `slice(0, 0)` or raise
  `IndexError` as `_index` does.
- **`util/_time_series.py:124-125`: gap interpolation of an integer series truncates toward zero** where the
  docstring says linear: appending `(0, 0)` then `(3, 10)` records `0, 3, 6, 10`. Round, or say so.
- **`protocol/_recording.py:71`: the default lzma preset makes recording ~12x dearer than needed**: 3.4 ms per
  recorded exchange at preset 6 against 0.3 ms at preset 1, for a file 20% larger. `record_to` is public on
  `run_local`/`run_ladder`, so a ladder bot recording pays this every observation.
- **`protocol/_recording.py` and `run.py:137-142`: file errors leak as bare `OSError`s.** An unwritable `record_to`
  fails after the websocket and game process are up, with `FileNotFoundError`; a request after `close()` raises
  `ValueError` from the lzma stream instead of `ConnectionClosedError`; a playback over a missing file constructs
  and fails on the first request with `FileNotFoundError`. Open the recording before connecting and translate
  `OSError` at those three points.
- **`launch/_game_process.py:130-145`: `wait_until_listening` accepts any listener on the port**, so a client that
  failed to bind (or a second client racing on `free_port`) is reported as up; **`launch/_game_process.py:23-28`:
  `free_port()` reserves nothing**, and 2000 consecutive calls returned 142 repeats. Confirm with a `ping` after the
  probe, and pick several ports while holding every probe socket open.
- **`launch/_installation.py:101-103`**: the not-found message names the default location even when `SC2PATH` was
  set to a wrong path; list what was tried.
- **`protocol/_client.py:212`**: `Result(entry.result)` reads an optional proto2 enum without `HasField`; unset it
  reads `Victory`. The game always fills it, so this is checklist hygiene.
- **Dead or half-wired API**: `Installation.replays` has no caller anywhere, and `Client.save_replay` none outside its
  test, while `run_from_command_line` accepts `--replay-file` as "not yet supported". Wire the flag or delete both.

### 2.5 Game data and the tech tree (each confirmed on the corpus tables)

- **`gamedata/_ability_data.py:120-128` (`_behavior`): arming a nuke reads `KEEPS_ORDERS`.** A nuke is no curated
  unit type, so `GHOST_ACADEMY_BUILD_NUKE` has no product and falls to the "no product, not a holder" branch, though
  it costs 100/100 and the sweep saw `Cancel_Queue5` offered while arming (`data/tech_tree.json`), so it is a queue
  item. The order book treats `KEEPS_ORDERS` as "carried out at once", so a nuke order never shows in
  `issued_to(include_sent=True)`, and `_production` cannot see it. The row reads `cancelled_by=CANCEL_LAST`, which
  is right, while two docstrings (`:174-178`, `:256-261`) say `CANCEL`. Class a priced ability on a structure as
  `QUEUES` even without a product, and fix the docstrings.
- **`tools/generate_tech_tree.py:300-345` (`_products`): the way back of every form change "makes nothing".**
  `LAND`, `UNSIEGE`, `UNBURROW`, `SUPPLY_DEPOT_RAISE`, `HELLION_MORPH_HELLBAT`, `HELLBAT_MORPH_HELLION`,
  `WARP_GATE_MORPH_GATEWAY` and the like all read `products={}`, because the tree records one creation ability per
  type. So `HELLION_MORPH_HELLBAT` is invisible to `api.in_production`, and `WARP_GATE_MORPH_GATEWAY` reads
  `KEEPS_ORDERS` while `GATEWAY_MORPH_WARP_GATE` reads `NEEDS_IDLE`. Either sweep each mode switch on its performer
  and record those morphs as products, or narrow the `products` docstring to "the ability that first makes each type".
- **`gamedata/_game_data.py:78-91` (`_read_table`)**: `except ValueError` is meant for an uncurated id but also
  swallows `Race(...)`, `Attribute(...)`, `TargetType(...)` failures inside `_from_proto`, so a value a patch adds
  would silently drop a curated row and surface later as a `KeyError`. Resolve the id first, read the row outside
  the `try`.
- **`gamedata/_unit_type_data.py:59-73, 102-157`**: `Weapon` and `UnitTypeData` are frozen dataclasses holding
  `MappingProxyType` fields without `field(hash=False)`, so `hash(row)` raises `TypeError`; `AbilityData` marks its
  mappings and the set test covers abilities only. Mark the fields, parametrize the test over every row type.
- **`gamedata/_ability_data.py:135-141` vs `:343-353`**: two `_performers` helpers with the same name differ; only
  one falls back from an `_OFF` toggle to its `_ON` half, so `AbilityData.performers` is empty for `HOLD_FIRE_OFF`
  and `BANELING_ATTACK_STRUCTURES_OFF` while their `order_behavior` was computed from the on half, and
  `tests/test_gamedata.py:403-414` special-cases `_OFF`. One helper.
- **`gamedata/__init__.py`**: `SentAs`, the type of the public field `AbilityData.sent_as`, is not exported, which is
  why `orders` imports `gamedata._sent_as` (1.2).
- Checked and clean: no aliased values in any curated enum; `_REMAPPED_IDS` consistent both ways;
  `ABILITIES_SENT_AS_ANOTHER` reads back as the id that sent it; speed and cooldown units; costs (every creation
  ability derives exactly one price); the generators cannot clobber `_overrides.py`; the upgrade reader gates every
  level, buff and health read on `IN_VISION`.

### 2.6 Geometry (each confirmed by a snippet)

- **`geometry/_point.py:275, 343-350`: `Point` arithmetic silently reads a `Tile`'s address.**
  `Point((1.0, 2.0)) + Tile(3, 4)` is `(4.0, 6.0)`, half a tile off the center a tile "reads as", while
  `point.distance_to(tile)` and `tile + point` raise as designed; the fast path `isinstance(other, tuple)` admits a
  `Tile`. Also `Point((3.0, 4.0)) == Tile(3, 4)` is `True` with equal hashes, so a tile and the point at its corner
  collide as dict keys. Fix the fast path with `type(other) is Point or type(other) is tuple` (measured free), and
  document the equality unless a `Tile.__eq__` measures acceptable.
- **`tile in area` is inconsistent across `Area` implementations**: `Tile(3, 4) in Rectangle(...)` and
  `in Circle(...)` raise `TypeError`; `in TileSet`, `in TilePath`, `in Tile` and `grid[tile]` answer. One shared
  membership helper that maps a tile to its center, and a `Tile` probe in `TestAreaAgreement`.
- **`geometry/_shapes.py:375-388`: `TileSet.closest_point_to` does not return the closest point.** For tiles
  {(1,10), (4,5), (6,4), (8,9), (10,8)} and probe (4.43, 2.87) it returns (4.43, 5) at 2.13 where (6, 4) lies at
  1.93; 133 wrong of 20 000 random probes, worst 0.19 off. The docstring admits it, but the name and the `Area`
  contract promise exactness. Verified fix: `query_ball_point(p, r=center_distance + sqrt(0.5))` after the KD-tree
  query and take the minimum (44 µs against 23 µs on 3600 tiles).
- **`geometry/_grid.py:366-369`: `distance_transform` ignores `outside=False`.** On a 5x5 grid true for y<3 with
  `outside=False`, column 2 reads `[3, 2, 1, 0, 0]`: the edge tile measures to the nearest false tile inside the grid
  rather than 1 to the ground beyond it. Pad with `False` before `distance_transform_edt` when `outside` is false.
- **`geometry/_grid.py:345-351`: `Grid.minimum`/`maximum` return the `NotImplemented` sentinel** (truthy, no
  exception) for an operand `_combine` rejects, e.g. `Grid.zeros(2, 2).minimum([1, 2])`. Raise `TypeError`.
- **`geometry/_circle.py:502-504`**: `Circle.translated` rejects a 3D offset the other three shapes accept.
- **`geometry/_shapes.py:35-36, 44-45`**: `Tile(1.5, 2.0)` is accepted and `Tile.containing` passes a non-integer
  through unfloored; validate in `__new__` (265 ns against 240 ns measured).
- **`geometry/_shapes.py:273-275`**: a zero-extent `Rectangle.random_point` returns a point not in the rectangle,
  where the `Area` docstring says an empty area raises.
- Checked and clean: `where_footprint_fits` against `fits_footprint` at every tile for asymmetric footprints,
  margins and every `outside` (0 of 4752 mismatches); `fill_footprint` against `Footprint.tiles`; `__radd__`/
  `__rmul__`; every `__contains__` returns a bool; numpy scalars; `path_distance_from`'s corner rule.

## 3. Algorithmic and performance

### 3.1 The placement grids are rebuilt from scratch on every observation (confirmed, measured)

On the corpus replay, taking in an observation costs 0.4 ms (tracker, state, upgrade inference, event report),
but the first `api.placement.is_free(...)` of a turn costs **2.4 ms median, 9.7 ms max** with ~160 units; a second
call in the same turn costs 0.1 ms. The cost is `dynamic` (one `fill_footprint` per present unit) plus
`_ground_townhalls_may_cover` (one per mineral field and geyser), both discarded at `_update`. Two cheap fixes:

- Cache the townhall ground across observations keyed by the frozenset of resource unit ids present; it changes only
  when a field is mined out.
- Make `dynamic` incremental, or at least vectorize it: build it once from the units whose footprint and position
  did not change (structures do not move) and refill only the ones that changed. Even without that, see 3.2.

### 3.2 `fill_footprint` spends a third of its time validating a default argument (confirmed, measured)

`Grid.fill_footprint(..., margin=0)` costs 7.7 µs, of which `_margin_sides(0)` is 2.7 µs: it builds a 4-tuple and
runs `isinstance(value, Integral)` (an ABC, which `docs/code-review.md` already warns is ~6x a plain check) four
times. The bare numpy assignment is 0.8 µs. A fast path `if margin == 0` in `_grown_by`, and `type(value) is int`
before the ABC in `_is_count`, would cut the per-unit grid work in 3.1 by about a third.

### 3.3 Geometry (each confirmed by a snippet)

- **`geometry/_grid.py:270-278` (`_scatter`): area indexing goes through Python `Tile` objects.** `grid[Circle]` of
  314 tiles costs 278 µs (558 µs for `+=`), where the bounding-box slices plus the boolean mask `Circle.tiles()`
  already computes give the same in 14 µs; `grid[tileset]` of 1600 tiles rebuilds its address array every call
  (482 µs against 8 µs cached). A virtual `Area._grid_selection(grid)` (slices for `Rectangle`, slices and mask for
  `Circle`, a cached address array on `TileSet`) is the shape the checklist prefers over an `isinstance` switch. No
  in-library caller is hot yet; this is the published way to build a threat map.
- **`geometry/_footprint.py:124-133` (`_grown_by`)**: the grown mask is rebuilt on every call with a margin
  (`fits_footprint` 10 µs plain, 30 µs with `margin=1`); `Footprint` is immutable and hashable, so memoize per
  `sides`.
- **`geometry/_tile_path.py`** has no `__iter__`, so `list(path)` goes through `__getitem__` per index (29 µs for
  300 tiles against 1 µs). Nothing produces a `TilePath` yet (see 1.6).
- `path_distance_from`: 19 ms on a 200x200 grid, once a game; fine.

### 3.4 Small per-observation costs worth a line each

- `_Production._ability_product` builds `set(row.products.values())` for every order of every own unit each turn;
  a `single_product` property on `AbilityData`, computed once, removes it.
- `Enemy.assume_upgrades` allocates a new frozenset every observation even when nothing changed (`|=` on an
  unchanged set), and `UpgradeReader.read_basic_upgrades` walks every unit; guard with `if not upgrades <= self._upgrades`.
- `Units.__contains__` scans the tuple; `_index()` already exists for an O(1) answer.
- `_BuildSites._builds_ordered_to` can yield the same build up to three times (issued, sent, shown) and fill the
  same site thrice; dedupe by `(ability, target)`.
- `PlacementGrids.reserved` is rebuilt on every property read (3 times a turn in the demo bot); a version counter on
  the order book would let it cache until an order or reservation changes.
